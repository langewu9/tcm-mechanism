# 数据库与任务列表性能审核（2026-10-20）

## 结论和范围

保留现有业务表划分，不拆结果表、不更换数据库。本轮只增加三个经过查询计划对照的索引、确定时间并列时的排序，并为当前前端接入轻量任务列表。原始数据、分析输入/结果、来源版本及研究算法不变；模型和外部生物数据库继续不调用。修改只保存本地 Git，没有推送。

## 任务列表与页面恢复

原列表把每条任务的完整 `result`、`input_parameters` 和来源版本都一起返回。蛋白组学页面和 R 图表目录直接用其中的结果恢复展示，不能简单删除这些字段。

新增 `GET /api/v1/research/analysis-tasks/summaries/`：

- 返回分页任务 ID、类型、状态、关联记录、进度、时间、错误摘要和所有者等元数据。
- `display_parameters` 只包含 `name`、`analysisKind`、`chartKey`、`parentTaskId`，分别在 SQL 中限制为 200、80、48、20 字符；字段可能为空。它不代表完整输入参数。
- 不选择完整 `result`、不把完整输入 JSON 传给 Python、不预取来源版本关系。数据库仍需读取输入 JSON 的相关键来生成展示字段，因此不能称完全避免该 JSON 的数据库内部读取。
- 沿用会话认证、所有者过滤、超级管理员权限、分页、任务类型/状态/父任务筛选和私有禁止缓存策略。
- 原 `/analysis-tasks/` 和详情接口保持完整响应，兼容现有工具、历史客户端和导出；OpenAPI 明确描述新增摘要接口。

当前 React 前端的两个列表读取点已切换到摘要接口：蛋白组学页面只额外读取选中的分析、富集图和火山图详情；R 目录只额外读取当前可展示图表中每种图最新任务的详情。不会把摘要当作完整结果。导航切换或组件卸载后，旧详情响应不能覆盖新页面；详情与摘要的任务 ID/类型/父任务不一致会报错。

布局、JSX 展示内容及 CSS 没有改动。生成 CSS 与上一轮逐字节相同，SHA-256 为 `e3fadffc6b745f1c962600d8bcd938af0d9544654734aba270d79cf62664b13e`。这不等同于全站像素验收。

### 真实 HTTP 对照

在原隔离 PostgreSQL 验收资料上，经 Vite 5174 → Django 8021，用同一研究者读取同一批 13 个任务：

| 项目 | 完整列表 | 摘要列表 |
|---|---:|---:|
| HTTP 响应体 | 644,862 字节 | 6,186 字节 |
| 数据库查询数（强制认证，不含会话） | 上轮已验证为 3 次 | 2 次 |
| 完整输入/结果 | 全部返回 | 从详情按需读取 |

**列表响应体减少 99.04%。这不是整页加载时间或整页总流量减少 99%。** 选中的任务仍需要完整详情，读取详情会增加请求、数据库查询和完整结果的传输；高网络延迟下的整页恢复时间还需另测。

实际 HTTP 验证确认新旧列表的 ID、顺序、总数一致；逐条详情与完整列表记录相等，保存了每个历史结果的哈希作为本地核对依据；其他研究者访问这些详情仍返回 404，摘要也按所有者隔离。没有创建新研究记录。

## 查询计划与索引选择

使用 `tools/audit_database_performance.py`，在现有隔离 PostgreSQL 上创建两张临时表，复制任务/同步记录的列与原有索引，各生成 60,000 条明确合成记录，分布为 200 个用户、40 个来源。只测读取，事务结束回滚，不往正式业务表灌数据。迁移后重跑时会先删除临时表中复制的新候选索引，确保旧基线不被污染。

每条查询先预热一次，再执行三次 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`，下表为迁移后重跑的三次执行时间中位数，单位毫秒：

| 查询场景 | 原索引 | 新索引 | 查询计划变化 |
|---|---:|---:|---|
| 某用户最新 50 个任务 | 0.257 | 0.038 | 用户索引筛选后排序 → 按复合索引读取 |
| 某用户最新 50 个蛋白组学任务 | 0.214 | 0.064 | 筛选并排序 → 按用户/时间索引读取并筛选类型 |
| 管理员最新 50 个任务 | 33.464 | 0.037 | 全表扫描后排序 → 按时间索引读取 |
| 某来源最新 50 条同步记录 | 4.379 | 0.039 | 来源索引筛选后排序 → 按来源/时间索引读取 |

这证明了特定查询形态的索引路径，不是公网吞吐、正式规模或端到端延迟承诺。这里用户平均只有 300 条任务，当前真实库更小，不能把这些倍数直接套到现有网页。

迁移 `core.0025_task_history_indexes` 添加：

| 表 | 新索引字段 | 用途 |
|---|---|---|
| AnalysisTask | owner、created_at 倒序、id 倒序 | 用户任务按时间分页 |
| AnalysisTask | created_at 倒序、id 倒序 | 管理员和全局最新任务 |
| SyncRun | source、created_at 倒序、id 倒序 | 某来源最新同步及同步历史 |

任务和同步记录默认排序均为 `created_at DESC, id DESC`，避免同一时间戳记录的分页顺序不确定；“最新同步”子查询也采用相同顺序。原用户/状态索引保留，用于按状态查任务。

在两张各 60,000 行的临时表上，三个索引合计增加约 6.5 MiB 索引空间；索引也会增加插入和更新成本，本轮没有测持续写入吞吐。没有为每个字段增加索引。

## 其余表的判断

- 数据集已有 owner/created_at，医案已有 owner/updated_at。当前按用户查看和时间排序与这些索引相符，暂不改；是否需要叠加归档条件，需要有代表性的归档比例和查询计划。
- 数据集行已有 dataset/row_index 唯一约束；蛋白组学结果已有 task/row_index 唯一约束及 task/selected、task/normalized_symbol 索引，本轮保持。
- 知识实体、外部编号、证据关系已有各自唯一约束、外键索引及部分业务索引。大规模模糊检索、JSON 条件和复杂图谱联查仍需正式目录规模验证，暂不增加推测性的全文/JSON/图谱组合索引。
- 任务结果暂不拆表。先通过投影与详情读取解决已确认的传输问题，再观察是否还有独立结果表或文件存储的必要。

## 重跑

本机隔离配置存在时：

```sh
python_app/.venv/bin/python tools/audit_database_performance.py
python_app/.venv/bin/python tools/smoke_task_summaries.py
```

执行计划、HTTP 字节数与历史结果哈希只保存在 Git 忽略的 `python_app/var/database-performance-audit/`。测试日志位于 `python_app/var/framework-audit/`，账号和连接凭据不提交、不打印、不外发。
