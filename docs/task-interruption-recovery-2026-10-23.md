# 后台任务中断与保守恢复（2026-10-23）

本轮处理现有后台任务的进程中断、终态覆盖和半结果发布，不增加研究算法或业务模块。没有修改 React UI、模型调用逻辑、来源身份判定、数据库模型或 migration；没有接入真实模型或外部科学接口。演练只使用单独创建的临时 PostgreSQL 数据库、Redis、专用队列及合成任务，不向现有验收库或队列投递演练任务，也不把合成输出当作科研结果。

策略是保留本次失败记录，由研究者或管理员明确新建下一次任务。**不把失败记录重置为排队，不自动重发，不自动重试模型或外部调用。** 已成功、已失败及已取消的历史任务不因中断通知而改写。

## 问题依据与实现

旧任务以条件更新领取 `queued → running`，可以阻止重复领取，但在进程强制退出后，普通 `except Exception` 没有机会把业务记录改为失败。消息重新投递时又因记录已为 running 而跳过，导致界面长期显示运行中。去掉领取条件、强制重跑同一记录会引入重复外部调用与结果覆盖风险，因此本轮没有采取该方式。

| 位置 | 本轮边界 |
| --- | --- |
| 七个现有业务 Celery 任务 | 使用统一 `RecoverableTask`；保留排队状态的原子领取，只允许 running 发布结果或失败状态 |
| `config/background_tasks.py` | prefork 父进程通过 `RecoverableRequest.on_failure` 处理子进程丢失/终止，通过 `on_timeout` 处理硬超时；普通未处理任务异常由 Task 回调补记。数据库不可用时不吞造成功状态，也不记录参数或凭据 |
| `core/services/task_recovery.py` | 仅接受明确允许的任务名与业务编号；中断更新仅为 running→failed，保留输入、所有者、来源及既有结果；旧执行在发布事务中锁定任务并再次检查 running |
| 医案分析 | 先锁医案、再锁分析任务；候选、来源关系、结果及成功状态同一事务发布。模型请求发生在持久化锁外；没有改候选提取或医学判断逻辑 |
| 图表任务 | R 请求在锁外；返回后检查任务仍运行，再将工件数据库记录、来源关系、结果及成功状态一起发布；普通异常继续清理本次已写文件 |
| 蛋白组学 | 进度与失败更新不能覆盖终态；最终锁定并检查任务后，才删除/新增逐行结果及发布成功；没有改统计、映射或筛选规则 |
| 独立外部分析 | 先完成原外部请求，再锁任务；新增/关联来源版本与成功结果同一事务。状态已经改变则不发布本次结果 |
| 完整本地证据 | 保留原快照、来源、成功状态的共同事务；发布条件不再成立时抛出 `TaskExecutionStopped`，整批回滚并返回 skipped |
| 入队失败 | 分析只允许 queued→failed，同步只允许 pending→failed，避免发布响应异常时陈旧实例覆盖已经运行或完成的任务；API 错误格式不变 |

普通研究者不增加维护入口。失败原因继续使用现有任务字段与页面显示，维护信息保留在后台和脱敏日志。

## 同步事务范围与尚存窗口

仅 `SQLITE_CONNECTOR` 本地路径增加外层事务：按 **DataSource→SyncRun** 顺序锁定、复核运行状态及来源启用状态，再执行原 preview/apply；目录变动、来源版本、计数及同步成功状态一起提交。该路径读取本地文件，不在锁内发送科学接口网络请求。强制退出若发生在提交之前，数据库事务应回滚，不能留下已经应用目录却仍显示 running 的新提交窗口。

Reactome、UniProt、PubChem、STRING 等外部同步本轮只补任务状态条件检查。其 connector 内部业务提交与 worker 最终成功状态仍可能分开：若刚完成目录/版本变动就退出，记录可能未显示成功。**不能把同步记录判失败等同于确认所有目录变动均已撤销。** 恢复后必须核对目录、来源版本及同步计数，再明确新建预览/应用；真实接口仍暂缓，后续接入时再处理各 connector 的内部发布边界。

蛋白组学 `integrations.py` 内部新增的全局 DataSource/SourceRelease 记录，仍可能早于 worker 最终发布事务。任务结果、逐行结果及任务与来源版本的关联已受保护，但不能宣称这些全局来源记录新增也会一并撤销。本轮没有扩改该文件，也没有运行真实外部服务。

## 手工维护命令

`fail_interrupted_tasks` 用于整个 worker 已消失、数据库暂不可用等不能由回调完成记录更新的情况。它是**维护命令，不是后台自动巡检或任务续跑器**。

1. 先确认维护环境及目标数据库，暂停所有任务生产者，包括可能提交任务的 API/计划任务，并停止全部 worker。不要只停止一个同名 worker 就认为其他主机没有执行。
2. 选择明确的带时区截止时间，仅纳入已核对的旧运行记录；先 dry-run 查看匹配数量。
3. 核实没有活跃执行、确认匹配范围后，才在维护窗口显式 apply。保留输出报告；失败任务后续由使用者明确发起新任务。

从仓库根目录执行的参数示例（时间须替换为本次实际核对的截止点；环境及数据库须事先配置并确认）：

```bash
python_app/.venv/bin/python python_app/manage.py fail_interrupted_tasks \
  --before "2026-10-22T23:59:00+08:00" --kind all
```

默认仅预览，不更新。`--kind` 可用 `analysis`、`sync`、`all`。确认维护窗口后，显式增加两个参数：

```bash
python_app/.venv/bin/python python_app/manage.py fail_interrupted_tasks \
  --before "2026-10-22T23:59:00+08:00" --kind all \
  --apply --workers-stopped
```

`--workers-stopped` **只是操作者对“所有 worker 和生产者已停止”的断言，不会自动探测活任务或其他主机**。截止时间也不是“超时即死亡”的判定。不要对仍在运行、等待模型或等待网络的任务使用该命令。

命令只匹配 `status=running` 且 `started_at <= before` 的记录；apply 时逐条锁定并再次检查，在 PostgreSQL 上跳过已被锁定的记录，不长时间等待它们。报告包括 `dryRun`、`matched`、`updated`、`skippedLocked`、`automaticRetry=false`、`workersStoppedAutomaticallyVerified=false`。行锁只能避免与提交事务冲突，不能证明锁外计算的任务已经停止；SQLite 不提供相同的 PostgreSQL 行锁语义。无 started_at 的旧异常记录不在该截止筛选内，应另行核对，不能扩大成无条件批量失败。

命令不删除数据或文件、不修改输入、不重置排队状态、不向队列发送消息。状态改变后仍存活的旧执行也不能复活结果，但已经发送的网络请求无法由数据库回滚撤回。

## 运行限制

- prefork 父进程仍存活时，才有机会处理子进程丢失或硬超时回调。整个父进程/主机被 SIGKILL、断电或崩溃，没有 Python 回调保证；依赖维护命令核对，不能承诺即时自动恢复。
- 父回调使用 PostgreSQL `skip_locked`，避免在杀子进程之前等待子进程持有的发布锁。若任务行或关联外键锁仍被占用，回调会跳过，记录可能仍为 running，需要维护命令核对；实测硬超时探针没有持长数据库事务，不能据此保证所有超时都即时 failed。行锁跳过也不等于数据库网络/连接故障不会延迟回调。
- 当前开发服务若使用 solo 池，没有独立 prefork 父进程替它捕获自身强制退出；也不能把配置了 Celery 时限等同于 solo 池已实际执行硬时限。实际支持范围须以对应池的演练为准。
- 回调写库时数据库不可用，失败状态可能无法落盘。回调只记录脱敏错误类型，稍后仍需停 worker 后人工核对；不能宣称诊断日志代替业务数据库的持久证据。
- 数据库事务不能自动撤回对象存储/文件系统的写入。图表普通异常已有本次文件清理，但 SIGKILL 恰发生在文件写入后、数据库提交前，仍可能留下无数据库工件记录的孤儿文件；它不应成为用户可下载结果。不能宣称本轮实现了所有崩溃下零孤儿文件，也没有自动删除疑似文件。
- 外部服务即使已接收请求，也可能因本地退出而未保存返回值；本轮不自动重复该请求，避免重复消费或不明确的远端副作用。
- Celery 任务类及 Request 在 worker 启动时加载，**必须正常重启 worker 才能使用最终修补**；仅刷新网页或重启 API 不足以加载 worker 内的新代码。重启前先确认维护窗口及未完成任务，不为演练强制终止实际业务 worker。

本轮不扩展生产部署、性能调优、模型服务、外部数据连接、隔离来源行或研究结果身份修订。后续结论以本节最终验收补记和对应原始日志为准。
