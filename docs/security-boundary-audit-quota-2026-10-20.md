# 管理后台、敏感访问审计与上传额度

后续文档权限补充：API 文档与原始 OpenAPI 定义已集中到 `/django-admin/platform-api/` 和 `/django-admin/platform-api/schema/`，沿用维护后台超级管理员权限；原 `/api/docs/`、`/api/schema/` 仅跳转到受保护的页面。后台首页增加接口文档入口。此步没有移除前端“接入监测”或“查看平台接口”入口，用户仍在确认两者用途；业务接口和接入测试逻辑未改。两种数据库各 14 项相关回归及严格 OpenAPI 校验通过。

本轮按用户指定顺序处理这三项。保留研究者页面、业务算法、原始上传和既有研究结果；不接入模型或外部生物接口，不改部署服务器、防火墙、MFA 或其他业务模块，不自动推送远程。

## 1. 后台权限与结果修改边界

- Django 维护后台统一要求账号有效、`is_staff` 和 `is_superuser` 同时成立。普通研究者及非超级管理员 staff，即使拥有模型权限，也不能通过列表、详情、直接 POST 或 autocomplete 进入后台。后台登录表单也拒绝非超级管理员登录。
- 业务 API 仍保留原有规则：研究者只能读取自己的数据，平台超级管理员可以查看全部。没有将前端传入的 owner 当作身份依据。
- 分析任务的归属、创建者、参数、结果和来源版本保持只读；后台禁止新增、修改和删除任务。蛋白组学行结果也不能通过后台修改或删除。数据集、医案的后台保存入口同样关闭，业务网页原有受控编辑、归档及审核流程保留。
- 计算程序仍可正常创建任务、推进状态和写入结果。本次没有添加重算或历史版本业务接口，也不对直接数据库操作宣称防篡改保护。

## 2. 敏感访问审计

新增 `SensitiveAccessEvent` 表，通过 Django 后台的 Sensitive access events 查看，只允许超级管理员只读查看。

覆盖研究数据集、医案和任务的列表、详情、摘要、行结果、医案候选/审计查询、原文件下载、图表下载、结果导出，以及研究总览、文本工作台、管理总览和对应维护后台的查看操作。操作失败不会登记为成功访问；匿名或越权请求继续按原有 401/404 等规则拒绝。

每条记录保存访问账号、时间、操作、入口、HTTP 方法/状态、请求编号，以及返回记录的类型、ID、所有者 ID。不会复制医案正文、文件名、文件内容、研究结果、查询条件、密码、Cookie 或 Authorization。单次最多记录 250 个对象引用，超出会明确标记截断；正常 API 分页与维护后台分页在此范围内。审计页查看自身不递归生成审计事件。

行结果、候选及医案操作历史以已校验权限的所属任务/医案编号追踪，不把每个结果行复制到访问日志。

如果审计写入失败，敏感 JSON 或文件响应会被扣留，返回安全的 503，不静默放行。文件响应发放记录不证明客户端已经完整接收文件。审计记录不允许通过管理网页手工修改或删除；本轮没有实施独立审计服务器、自动清理或数据库级防篡改。

每个成功的敏感读取请求增加一次审计写入。原有分页/预取仍保留：受控查询预算下，任务列表是 3 次读取加 1 次写入，数据集列表和任务摘要是 2 次读取加 1 次写入。此前压测报告基于开启本次访问审计前的代码，本轮没有重新压测。

## 3. 上传额度与调整方法

默认每个账号累计 **1 GiB 原始上传、100 个数据集**。单文件仍最多 100 MiB，并继续执行原有格式和解析限制。归档文件仍保留，因此继续计入容量和数量。超级管理员自己上传也使用相同规则。

在 **Django 管理后台 → Users → 选择研究者 → 研究资料上传额度** 查看当前占用，并在同页“研究资料上传额度”内联表单修改：

- 累计容量以 MiB 填写，`1024` 为 1 GiB，`2048` 为 2 GiB。
- 数量填写该账号可以累计保留的数据集数。
- 留空表示使用平台默认值；填 `0` 表示不再接收新上传。
- 下调额度不会删除、归档或重写已有数据，只会阻止继续超额上传。调整后直接按新额度检查后续上传，不需要修改代码或重启。
- 保存调整人、调整时间及调整前后的额度值。普通 staff 不能修改额度。调整审计与额度更新处于同一后台保存事务。

平台默认值由 `DATASET_STORAGE_QUOTA_BYTES=1073741824`、`DATASET_COUNT_QUOTA=100` 配置。全局默认配置更新需要重启相应服务；单账号覆盖值优先于默认配置。`GET /api/v1/research/datasets/quota/` 只返回当前登录账号的占用与有效额度，忽略其他账号的查询参数。

上传前检查累计额度，超限返回统一 JSON 错误 `409 / UPLOAD_QUOTA_EXCEEDED`，不保存新文件。解析失败及上传溯源记录失败会回滚记录并清理本次文件。PostgreSQL 在同一个上传事务内锁定用户行，随后检查额度并保存文件与数据；管理员额度调整也在同一用户行锁下完成，避免并发抢占最后一个名额。

额度目前针对上传的原始数据集，不包含医案文本、分析结果或生成图表。SQLite 仍用于本地开发，不作为多进程并发额度保证的生产数据库。

## 迁移与验证

新增迁移 `0026_sensitive_access_audit`、`0027_researcher_upload_quota` 只创建审计和账号额度两张表，没有数据迁移，不删除或修改旧研究记录。部署时先执行迁移，再启动加载新代码的 API；生产 setup 服务仍按现有流程执行迁移。

新增回归覆盖后台权限、结果只读、审计脱敏/失效拒绝、额度调整、归档计费、超额前拒绝、失败清理和 PostgreSQL 并发争抢。测试使用临时数据库及合成文件，不调用外部模型或生物数据接口。日志位于 Git 忽略的 `python_app/var/framework-audit/security-*.log`。

- PostgreSQL：448 项全部通过，72.667 秒；最后一个上传名额的两条并发请求分别为 201、409，只保存一个数据集和一个文件。
- SQLite：448 项中 447 项通过、1 项跳过，46.525 秒；跳过的是其不支持的 `SELECT FOR UPDATE` 并发保证测试。
- OpenAPI 严格校验、迁移一致性和 Git 空白检查通过。研究者前端源文件没有改动，本轮未重跑无改动的前端构建。
- 隔离 PostgreSQL 预览已应用两项建表迁移。迁移前后核对 10 张既有研究表的行数和完整记录 SHA-256，均一致；没有重算历史结果。对照保存在忽略的 `security-preview-migration.json`。
- 隔离预览 API 已重启以加载本次代码。旧 SQLite 预览和研究资料没有覆盖；未推送远程，也没有把本轮结果视为正式服务器安全验收。
