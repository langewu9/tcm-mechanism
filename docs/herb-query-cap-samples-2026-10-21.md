# 中药查询限额样例测试（2026-10-21）

## 方法与范围

按记录量分层选取 8 个来源内单药样例，测试 300、600、1,200、2,400、4,800、12,000 六档关系限额。每档预热 1 次，再串行测量 3 次取中位数。测试现有生产查询函数，没有修改当前平台的额度。

| 来源 | 样例 | 分层依据 | 完整三元组行 | 来源靶点实体 |
| --- | --- | --- | ---: | ---: |
| HIT | 牛角尖粉 | 原始行数中位附近 | 73 | 67 |
| HIT | 野山楂 | 原始行数 P90 附近 | 566 | 341 |
| HIT | 石榴皮 | 此前核验样例 | 1,002 | 513 |
| HIT | 紫河车 | 原始行数最大值之一 | 4,427 | 1,577 |
| TCMSP | 白茅根 | 原始行数中位附近 | 470 | 225 |
| TCMSP | 月季花 | 原始行数 P90 附近 | 1,375 | 398 |
| TCMSP | 石榴皮 | 跨来源对照名称 | 480 | 236 |
| TCMSP | 麻黄 | 原始行数最大值 | 3,919 | 1,058 |

上述样例在各自来源中的完整、有名称的三元组记录均提取，不只截取前若干行；另外每个来源选取前 2,000 条非样例完整记录作为有界背景。总计 16,312 条来源行，使用现有导入投影生成测试实体和关系。62 行缺项记录没有清洗或补齐，不属于本轮具备完整字段的测试样本。

通过独立临时 PostgreSQL 库运行，结构使用现有 Django migrations；查询采用修复后的数据库来源筛选。临时数据只供本次测量，不写当前验收库，不调用模型或外部数据服务。

“完整”必须同时满足返回靶点实体集合、来源关系记录集合与样例基线一致。只比较靶点个数不够；同一靶点的多条证据不能因为实体去重就丢失。单药同时测批量检索和网络中药侧输入。网络疾病词固定为不存在的测试名称，不代表任何真实疾病，不能把本轮耗时当作完整疾病机制、图表或外部接口分析耗时。

另测七个不同药名的联合查询。名称检索会匹配抽样库中所有启用来源的同名实体，因此除八个主样例来源身份键外，还包括 HIT 背景中的一条白茅根记录；联合基线共九个来源内中药身份键。它仅代表这份抽样目录中的联合数据，不能当作七味药在两份全库中的完整联合结果。

首次联合基线仅合并八个主样例、漏算上述一条背景记录，严格集合校验因此终止。修正测试基线后重新测量；首次日志保留，最终表格只使用重测结果。未把该测试脚本遗漏误报为业务查询串联。

计时包含服务函数查询/结果组织及额外 JSON 序列化，不含网络传输、浏览器渲染、认证审计、并发或真实疾病侧计算。使用本地开发配置和有界背景，未复现生产全库规模；返回体积是带临时来源版本标记的未压缩 JSON 字节，不能视作生产逐字节响应或公网容量承诺。三个测量值只用于初步比较，不推算 P95、并发量或生产 SLO。

来源文件保持原字节不变：HIT 工作簿 SHA-256 为 `8d9f3fa51f6c12d55799acd3cef8cf9a9be3ef99fc3be62a04e093f7614ad1e0`；TCMSP 为 `1482cd795f3396b917bebf74046009a1a529e71c2984d8aa376fa4069777d986`。来源物种和权威标识仍未确认，本轮不检验生物学有效性。

## 多药联合与导出限制

本次抽样库中，七个药名实际匹配九个来源内身份键，完整基线有 12,313 条三元组、2,758 个来源靶点实体；包括前述 HIT 白茅根的一条背景记录。

| 网络阶段限额 | 读取的三元组证据对 | 来源靶点实体 | 来源关系覆盖率 | 输入是否截断 |
| ---: | ---: | ---: | ---: | --- |
| 1,200 | 1,200 / 12,313 | 519 / 2,758 | 9.75% | 是 |
| 4,800 | 4,800 / 12,313 | 1,391 / 2,758 | 38.98% | 是 |
| 12,000 | 12,000 / 12,313 | 2,739 / 2,758 | 97.46% | 是 |
| 24,000（完整基线） | 12,313 / 12,313 | 2,758 / 2,758 | 100% | 否 |

12,000 档仍少 313 对来源行证据、19 个来源靶点实体，中位耗时约 5.01 秒。24,000 是单次完整性基线，没有做三次耗时比较，不能据此推荐统一调高到该值。

网络原始表还有独立的 4,000 行限制：紫河车输入已完整时，仍只返回 4,000 / 4,427 行；联合输入完整基线仍只返回 4,000 / 12,313 行，并正确标记原始表截断。本次不含真实疾病侧分析、1,000 条候选靶点展示以及 2,000 图节点/4,000 连线边界的验收，不能把“输入完整”写成整个业务输出都完整。

## 初步限额建议

1. 保留批量检索的 1,200 作为当前交互预览保护上限，必须继续提示部分结果。它不能充当完整科研输入的保证。
2. 单药完整读取可把 **4,800** 作为下一步候选档位；本轮八例及两份文件的完整三元组行数分布均支持这个候选。完整数据应考虑在后台处理或分页获取，避免页面一次承接接近 7 MB 的响应。分页能力本次没有新增。
3. 网络默认 12,000 对八个单药样例已经足够；多药联合仍可能截断。完整分析应检查输入范围，超限时分批/分页或转后台完整任务，不能只用靶点总数判断成功，也不能简单把全站改成更高的固定值。
4. 完整来源证据导出需要单独处理 4,000 行的限制，不能靠提高查询上限解决。

这些是两份来源、八个单药样例和一组抽样联合查询的初步建议。其他来源、更大的完整目录、真实疾病侧、网络传输和并发尚未实测，因此没有修改当前配置，没有声称确定了公网最终额度。
